# Поиск и кеш: принятое решение

Цель — **быстро открывать уже загруженную почту, а всю историю искать на сервере**. IndexedDB хранит рабочий кеш, без предварительного скачивания всего ящика. Реализация кеша начинается после коммита исправлений аудита #8 и их регрессионных тестов.

## Исходное состояние до IndexedDB

- В `chrome.storage.local` находятся настройки, учётные данные и последние метаданные входящих: до 50 писем на ящик.
- В памяти страницы находятся до 30 переписок, страницы папок и результаты поиска. Закрытие страницы освобождает их.
- Gmail API, Microsoft Graph и JMAP выполняют серверный поиск: сейчас до 20 результатов на ящик, без загрузки следующей страницы.
- Для браузерных подключений Gmail, Яндекса и Mail.ru адаптеры поиска ещё не реализованы. Интерфейс сообщает об исключённых ящиках.
- Аудит #8 исправляет гонки действий и поиска, полное падение поиска, лишнюю инвалидацию переписок и ограничивает HTTP-параллелизм восемью запросами.

## Хранилище

Используем **нативную IndexedDB только в worker**, без новой зависимости. Chromium поддерживает её в service worker расширения: [документация Chrome](https://developer.chrome.com/docs/extensions/develop/concepts/storage-and-cookies). Сохранность данных в установленном Safari 16.4+ проверяется отдельно.

Учётные данные и настройки остаются в текущем хранилище. Кешируем данные, полученные обычным открытием входящих, папки, переписки или серверным поиском. Вложения и внешние картинки автоматически не скачиваем.

| Хранилище  | Ключ                                         | Данные                                                                                                                   |
| ---------- | -------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------ |
| `messages` | ID ящика + ID письма                         | Метаданные и флаги; исходные HTML/текст тела, если загружены; описания вложений; время получения/доступа; оценка размера |
| `views`    | ID ящика + тип + идентификатор представления | Упорядоченные ID писем, непрозрачный курсор, время получения, полнота результата                                         |

Индексы по ящику и времени доступа нужны для удаления и вытеснения. Тело письма хранится один раз для всех представлений. Вытеснение письма делает связанное представление неполным; недостающее тело запрашивается по требованию. Готовый iframe-документ не сохраняется: исходный HTML проходит текущий sanitizer при каждом показе, с действующими темой, согласием на картинки и CSP.

Начальные ограничения:

- 50 МиБ оценочного объёма, с обработкой меньшей квоты браузера;
- не более 5000 писем и 1000 представлений;
- вытеснение по последнему доступу и удаление данных, не использовавшихся 30 дней;
- без разрешения `unlimitedStorage`.

Недоступность IndexedDB, ошибка квоты или повреждённая запись не должны блокировать чтение через сеть. Удаление ящика очищает его кеш; проверка поколения запрещает позднему запросу записать данные удалённого ящика. Нужна отдельная очистка кеша в настройках. Перед передачей сборки обновляем `PRIVACY.md`.

## Открытие и обновление

1. Сразу показываем сохранённое тело/представление. Одновременные запросы одной переписки объединяем.
2. Устаревшие или изменившиеся данные перепроверяем в фоне. Текущее письмо и прокрутка остаются на месте; неизменившееся тело сохраняет iframe.
3. Показ кешированного непрочитанного письма не отменяет запрос отметки прочтения. Флаг меняется после подтверждения провайдера.
4. Подтверждённые действия защищены от старых ответов. Флаги и связанные представления обновляются атомарно; ответ на письмо инвалидирует свою переписку. Изменения другой переписки не сбрасывают текущую.
5. При сетевой ошибке сохраняем содержимое и показываем локализованный статус актуальности/ошибки. Ошибка не превращается в успешный пустой результат.

Начинаем с перепроверки загруженных представлений и инвалидации после действий. Полный движок синхронизации не требуется. При необходимости дальнейшей оптимизации доступны [Gmail history](https://developers.google.com/workspace/gmail/api/guides/sync) и [Graph delta](https://learn.microsoft.com/en-us/graph/delta-query-messages), но восстановление их курсоров зависит от провайдера.

## Серверный поиск

Запрос выполняется отдельно для каждого подходящего ящика. Следующий этап контракта должен возвращать результаты, непрозрачный курсор и статус успеха/ошибки/полноты каждого ящика. Объединяем и устраняем дубликаты по ID ящика + ID письма. Следующую страницу загружаем по требованию; первые 20 результатов не выдаём за всю историю.

| Подключение             | Контракт и дальнейшие действия                                                                                                                                                                                                                                      |
| ----------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Gmail API               | `messages.list.q`, `pageToken`, `nextPageToken`: добавить пагинацию и явно определить включение Спама/Корзины. [Справочник](https://developers.google.com/workspace/gmail/api/reference/rest/v1/users.messages/list)                                                |
| Outlook / Microsoft 365 | `/me/messages?$search=...`: валидировать продолжение; учитывать документированный предел 1000 результатов и области сопоставления. [Документация Graph](https://learn.microsoft.com/en-us/graph/search-query-parameter?tabs=http#use-search-on-message-collections) |
| JMAP                    | `Email/query` с `text`, `position`/`anchor`: использовать существующую основу пагинации и возможности сервера. [RFC 8621 §4.4.1](https://www.rfc-editor.org/rfc/rfc8621.html#section-4.4.1)                                                                         |
| Браузерный Gmail        | Atom feed не обеспечивает поиск всей истории. По решению владельца поиск пока выполняется через отдельное подключение Gmail API; мост к вкладке отложен                                                                                                             |
| Яндекс и Mail.ru        | Нужен отдельный адаптер поиска на основе фактического запроса веб-почты, проверки владельца, ответа и продолжения                                                                                                                                                   |

Для сессионных адаптеров проверяем обычный поиск в подключённом браузере: совпадение, пустой результат, несколько страниц, истёкшая сессия и другой ящик. Обезличенные ответы становятся фикстурами. Запросы идут через `background/http.ts`. Приёмка обязательно включает нахождение письма вне всех кешированных представлений.

Проверенные публичные источники не задают HTTP-контракт такого поиска: [Яндекс API для доменов](https://yandex.com/dev/domain/index/) описывает администрирование, [справка Mail для разработчиков](https://help.mail.ru/developers/) — другие интеграции. Это недостаток подтверждённого контракта, а не доказательство невозможности поиска. [Язык запросов Яндекса](https://yandex.ru/support/yandex-360/customers/mail/ru/web/letter/query-language) описывает синтаксис. [Настройки почтовых программ Mail](https://help.mail.ru/mail/login/mailer/) описывают IMAP; отдельный нативный мост изменил бы требование работы без дополнительных программ.

Кеш результата того же запроса и состава ящиков можно показывать до ответа сервера, с отметкой актуальности. Поиск только по загруженным данным — отдельная явно обозначенная область; он не заменяет неудавшийся серверный поиск. Частичные ошибки должны быть видны рядом с успешными результатами; полная ошибка требует повтора. Расширенные операторы зависят от провайдера.

## Пример Telegram

В [форке tweb владельца, e26b7de](https://github.com/ziqq/tweb/tree/e26b7de58a029d65083561fbe202b72b11571b18) есть [хранилища IndexedDB](https://github.com/ziqq/tweb/blob/e26b7de58a029d65083561fbe202b72b11571b18/src/config/databases/state.ts), [AppStorage](https://github.com/ziqq/tweb/blob/e26b7de58a029d65083561fbe202b72b11571b18/src/lib/storage.ts) и [карты сообщений в памяти с серверными запросами истории/поиска](https://github.com/ziqq/tweb/blob/e26b7de58a029d65083561fbe202b72b11571b18/src/lib/appManagers/appMessagesManager.ts). [Сохранение диалогов](https://github.com/ziqq/tweb/blob/e26b7de58a029d65083561fbe202b72b11571b18/src/lib/storages/dialogs.ts) включает снимок верхнего сообщения. Подход поддерживает кеш плюс серверный поиск, без обязательного локального индекса всей истории.

## Порядок внедрения и приёмка

1. Worker-хранилище IndexedDB, удаление данных ящика, ограниченное вытеснение; повторное открытие загруженных тел после закрытия popup.
2. Фоновая перепроверка без скелетона поверх загруженного письма, согласование подтверждённых действий, статус актуальности и очистка кеша.
3. Пагинация серверного поиска и отдельные статусы ящиков без смешивания поколений запросов.
4. Проверка и реализация сессионного поиска Яндекса и Mail.ru. Для Gmail пока используется отдельное подключение Gmail API; мост к вкладке отложен по решению владельца.

На каждом этапе измеряем холодное/повторное открытие, число HTTP-запросов и объём данных. Размеры интерфейса: 780×600, 400×600, 1440×900 и 390×844. Установленные Chromium и Safari проверяем отдельно. Сохранённое тело должно приходить до задержанного сетевого ответа, в том числе после перезапуска worker и страницы. Дополнительно проверяем квоту, вытеснение, удаление ящика во время записи, гонки read/pin, согласие на картинки/CSP и поиск незагруженного письма. Постоянные регрессионные тесты добавляются после подтверждения реализации, согласно `AGENTS.md`.

## Ход внедрения: 0.0.37

Первый этап реализует запись загруженных метаданных/тел и представлений, повторное открытие тела из IndexedDB, фоновую сетевую перепроверку, статус сохранённой копии, очистку в настройках, ограничения и защиту от поздних записей. Представления папок/поиска пока только записываются: чтение их до ответа сети остаётся следующим этапом. Поиск продолжает выполняться на сервере; новые сессионные адаптеры не входят в этот этап. В 0.0.38 после подтверждения реализации добавлены постоянные тесты настоящей IndexedDB, MV3, брокера и сетевого fallback.
