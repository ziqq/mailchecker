# OAuth и публичная политика: подготовка релиза

Проверено 16 октября 2026 года. В этом этапе изменены документы, текст политики и упаковка магазинного ZIP; runtime OAuth и тесты не менялись. По прямому решению владельца основной `ziqq/mailchecker` переведён в публичный режим. После отдельного разрешения актуальный `PRIVACY.md` опубликован одним коммитом; остальные локальные коммиты и тег не отправлялись. По отдельному разрешению ZIP 0.0.41 загружен в Chrome Web Store и создан черновик без отправки на проверку.

## Что показал Codetree

Публичная [карточка Codetree](https://chromewebstore.google.com/detail/codetree/omfcokfhgbjklkbkbhfadefpolbndjba) показывает опубликованную версию **0.4.1** и ведёт на [PRIVACY.md в GitHub](https://github.com/ziqq/Codetree/blob/main/PRIVACY.md). Репозиторий Codetree публичный. Отдельный GitHub Pages-сайт для этой схемы не нужен.

При этом GitHub/GitLab OAuth ID Codetree в исходниках пустые, опубликованная карточка описывает PAT-подключения. Это рабочий пример публикации и политики, а не доказательство готового OAuth для Gmail или Microsoft.

В Actions Codetree присутствуют имена четырёх `CWS_*` секретов. В mailchecker таких имён пока нет; значения не извлекались. CWS OAuth нужен для загрузки расширений и не заменяет Gmail OAuth.

## Политика конфиденциальности

Владелец выбрал GitHub-ссылку, как у Codetree, и явно попросил сделать основной mailchecker публичным. Подготовлен актуальный [PRIVACY.md](../PRIVACY.md): дата, контакт разработчика, локальное хранение и IndexedDB, разрешения, прямые обращения к провайдерам, серверный поиск, картинки и Limited Use. Контакт `a.a.ustinoff@gmail.com` совпадает с публичным контактом разработчика в Codetree.

Репозиторий [ziqq/mailchecker](https://github.com/ziqq/mailchecker) переведён в `PUBLIC`; отдельный `mailchecker-privacy` не создаётся. До смены видимости проверены все доступные GitHub refs: 53 коммита, 523 уникальных blob, из них 491 текстовый, а также 8 issue/PR и 1 комментарий. Поиск распространённых форматов приватных ключей, API-токенов и секретных строковых присваиваний не обнаружил совпадений. Это ограниченная проверка перед публикацией, а не гарантия отсутствия любых секретов.

Постоянная ссылка политики — `https://github.com/ziqq/mailchecker/blob/main/PRIVACY.md`. Актуальный текст опубликован [коммитом b7e8549](https://github.com/ziqq/mailchecker/commit/b7e8549b5d8f250ba2edf5ffc173eccb613bea20) поверх удалённого `main` `7176330` (код 0.0.13). В коммите изменён только `PRIVACY.md`; сохранено `Co-authored-by: ziqqineyo <a.a.ustinoff@yandex.ru>`. Публикация выполнена через GitHub Contents API, чтобы не отправлять остальную локальную историю. Локальный `main` остаётся на `803a6a4` с незакоммиченными изменениями 0.0.42; рабочее дерево не переключалось и не перезаписывалось.

Анонимный GET `https://raw.githubusercontent.com/ziqq/mailchecker/main/PRIVACY.md` вернул HTTP 200. Опубликованные 4717 байт совпали с локальным `PRIVACY.md` и документом в ZIP 0.0.41. SHA-256 политики: `950adff1288c3a3e090342e8643db8fb8515453b7515d53110fe8bc99849da2c`. [CI коммита политики](https://github.com/ziqq/mailchecker/actions/runs/38891805308) завершился успешно; это проверка удалённой ветки с кодом 0.0.13, а не CI локальной сборки 0.0.41.

Для Chrome Web Store это повторяет фактическую схему Codetree. Google OAuth verification — отдельная проверка: Google требует главную страницу и политику на одном подтверждённом домене. Успешная публикация GitHub-ссылки сама по себе не подтверждает прохождение Google. Если Google потребует подтверждение собственного домена, этот вопрос нужно будет решить верификацией подходящего сайта либо уточнением требований у команды проверки, а не обещать готовность заранее. [Требования Google](https://developers.google.com/identity/protocols/oauth2/production-readiness/brand-verification).

## Что требуется от владельца

1. **ID mailchecker в Chrome Web Store получен:** в [черновике](https://chrome.google.com/webstore/devconsole/f3cf73d3-37ce-4ab4-88a4-5cb1fce26075/bkddpiocidbcpklaoooaabfpgknijamg/edit/package?hl=ru) проверены версия 0.0.41, статус «Черновик» и отсутствие опубликованной версии. ID `bkddpiocidbcpklaoooaabfpgknijamg` отличается от нынешнего unpacked ID `fbojnpjcjilajbfjfhipjkldidjmmolo`. Публичный ключ сохранён в [OAUTH.md](OAUTH.md#verified-store-identity); его SHA-256 даёт ровно ID магазина. Следующий шаг — согласовать локальный ID с магазином в новой patch-сборке перед OAuth-настройкой. На проверку черновик не отправлять. Пошаговая инструкция — в [CHROME_WEB_STORE.md](CHROME_WEB_STORE.md#первая-загрузка-только-черновик).
2. **Google:** отдельный проект `mailchecker-511814` уже создан владельцем и выбран для дальнейшей настройки. Предложение касается внутренней реализации кнопки «Через Google»: вместо текущего получения токена через окно Google использовать штатный механизм Chrome, который получает токен и управляет его кешем/истечением. Владелец попросил объяснение; замена ещё не согласована. После выбора реализации создать OAuth-клиент, включить Gmail API и подготовить согласие на `gmail.modify`. Для предлагаемого варианта нужен клиент типа Chrome Extension, привязанный к Item ID. Передать только публичный Client ID `…apps.googleusercontent.com`. Инструкция «создать Web application и вставить ID» не подходит к предлагаемому новому пути. Выбор и проверка нескольких Gmail-ящиков обязательны: наличие параметра `account` у API не доказывает корректный выбор всех адресов, а `getAccounts` доступен только в dev-канале Chrome. Протокол входа не меняется до согласования.
3. **Microsoft:** создать Entra app mailchecker для личных и рабочих аккаунтов, добавить SPA redirect с окончательным ID и delegated Graph permissions `User.Read`, `Mail.ReadWrite`, `Mail.Send`. Передать Application (client) ID GUID. Секрет приложения не создавать. Точный путь и пояснение SPA — в [OAUTH.md](OAUTH.md).
4. **Автозагрузка CWS:** настроить в GitHub Actions mailchecker `CWS_EXTENSION_ID` для нового элемента и действующие `CWS_CLIENT_ID`, `CWS_CLIENT_SECRET`, `CWS_REFRESH_TOKEN` того же publisher. Для трёх последних можно использовать подходящий существующий доступ Codetree, если исходные значения сохранены. GitHub не выдаёт значения secrets обратно. Их не присылать в чат и не коммитить.

Владелец создал отдельный Google Cloud проект `mailchecker-511814` (название `mailchecker`, номер `1014715555178`); его данные подтверждены в Dashboard. Настройка продолжается в нём. Это заменяет прежний выбор общего проекта `github`; его настройки Codetree не менялись. OAuth-клиенты mailchecker пока не созданы. Не требуется присылать пароли, приватный ключ расширения, токены ящиков или клиентские секреты.

## Что сделает агент после получения этих данных

- Согласует и реализует Google token flow, затем подставит правильные public Client ID. Набор поддерживаемых аккаунтов нельзя молча сузить до одного Chrome-профиля.
- Проверит установленную сборку: согласие/отмена, несколько адресов, чтение и поиск, 401/истечение, обновление Microsoft, пробуждение worker и удаление аккаунта.
- Выпустит следующую patch-сборку после изменений runtime и после подтверждения реализации добавит регрессии. Загруженная в черновик 0.0.41 содержит подготовленную политику и массовое удаление, но не настроенный Google/Microsoft OAuth.
- Перед отправкой повторно сверит карточку, публичную политику, конфигурацию пакета и CWS-статус. Отправка на проверку и публичная доступность — отдельные результаты.

## Проверено в этом этапе

- Чистое исходное дерево `803a6a4` перед правками; отсутствие public Client ID и CWS-секретов mailchecker.
- Публичная карточка/политика Codetree, имена его CWS-секретов; без изменения Codetree и без чтения значений секретов.
- Текущие официальные требования Chrome, Google и Microsoft; legacy-статус Google implicit и необходимость правильного типа Microsoft redirect.
- Изолированный MV3-запрос с фиктивными данными подтвердил финальный `Origin: chrome-extension://…` на обмене Microsoft. Это подтверждение транспорта, не живой OAuth-вход.
- После проверки истории выполнена разрешённая смена видимости `ziqq/mailchecker` с `PRIVATE` на `PUBLIC`; GitHub API подтвердил результат. Локальные коммиты и правки не отправлялись.
- После отдельного разрешения опубликован только `PRIVACY.md` коммитом `b7e8549`; проверены состав коммита, соавторство, зелёный CI и анонимный публичный текст. CRC, SHA-256 ZIP 0.0.41 и совпадение вложенной политики проверены повторно.
- В Chrome владельца открыт существующий publisher `f3cf73d3-37ce-4ab4-88a4-5cb1fce26075`; системный Google Touch ID подтверждён владельцем. Установленный Codetree не изменялся.
- Реальная первая загрузка выявила запрет поля `key` в магазинном manifest. Упаковщик и его побайтный verifier теперь одинаково исключают это поле, не меняя unpacked manifest. Повторная упаковка дала идентичные байты; 31 файл, CRC, SHA-256 и неизменность остальных runtime-файлов/политики проверены отдельно. SHA-256 принятого на повторную загрузку ZIP: `99c41f6a5589eddfb9807bd40a149559cbabd5ac90945bc69bd727b6e9efe9e2`.
- После исправления упаковки `npm run verify` прошла: 212 тестов, форматирование, ESLint, TypeScript, repository checks, сборка и ZIP. Изменений клиентского runtime на этом шаге нет; браузерные UI-регрессии повторно не запускались.
- После повторной загрузки во вкладке Package подтверждены версия 0.0.41, 13 языков, разрешения, статус «Черновик» и отсутствие опубликованной версии. Из диалога прочитан публичный SPKI-ключ; его SHA-256 `1a33f8e28312fab0eee0015f6ad890c68850f765bc2026ddd66c05df8f5f8d67` даёт ID `bkddpiocidbcpklaoooaabfpgknijamg`. Исходный development-ключ не заменён.
- Карточка сохранена как созданный магазином черновик; описание, изображения и Privacy practices ещё не перенесены. Отправка на проверку, регистрации OAuth-приложений, пользовательский consent и успешный OAuth не выполнялись.
